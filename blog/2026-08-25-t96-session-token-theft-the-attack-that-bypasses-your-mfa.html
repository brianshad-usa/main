The Cookie That Walks Past Your MFA

MFA verifies one moment; the session token it issues is what attackers now steal. Why executives should measure revocation speed instead of MFA coverage.

Pro Link SystemsInsights
August 25, 2026 · Updated November 21, 2026
7 min read
In this article
  1. A token is a signed statement that the argument is over
  2. The change is industrial, not technical
  3. MFA is an event. Access is a state.
  4. Revocation latency is the number nobody measures
  5. Three questions before your next security renewal

An attacker holding your session cookie never sees your login page. There is no password prompt, no approval request on your phone, nothing to deny. The session was already approved, by you, an hour earlier, on a screen you had every reason to trust.

This is the part of the identity story many companies skipped. The multi-factor authentication (MFA) rollout was run as a project with an end date. It finished. A green square went onto a board slide. What did not stop was the search for the cheapest way in, and that path now runs through the artifact MFA produces after it succeeds. The argument here, for executives and the IT leaders who report to them, is to measure how fast you can end a session rather than how many people enrolled.

A token is a signed statement that the argument is over

When someone authenticates to Microsoft 365 or any modern cloud application, the platform does not re-verify identity on every click. That would be unusable. Instead it issues a token: in effect a signed statement that this browser, for a defined window, is that person. The browser holds it. Every subsequent request presents it. The service honors it without asking again.

The design is correct. It is also the exposure. A password is a secret you know; a token is a secret your device holds. Steal the token and you inherit the answer to a question that was already asked and already approved. Multi-factor authentication protects the asking. It has nothing to say about the answer once that answer is in someone else's hands.

Security teams have understood this for years. What has changed is how ordinary the attack has become.

The change is industrial, not technical

Session hijacking is old. Two well-documented routes now make it routine rather than specialized, and they converge on the same outcome.

The first is adversary-in-the-middle phishing. Rather than a fake login page harvesting credentials, the attacker's infrastructure relays the victim's traffic to the real login page in real time. The password is typed into a genuine Microsoft page, rendered through a proxy. The push notification is approved. Authentication actually succeeds, and the proxy captures the resulting session cookie on the way back. Analysis, not fact: the meaningful shift is packaging rather than invention. A related kit that the FBI described in May 2026, offered as a service with lures, templates and dashboards, hands Microsoft 365 tokens to operators with little technical skill by abusing the device code sign-in flow.

The second is information-stealing malware, delivered through a browser extension, a cracked utility, or a convincing installer served by a search ad. The payload's purpose is collection rather than encryption. It copies browser cookie stores, saved tokens and credential databases, often without lingering. Defenses tuned to ransomware behavior have comparatively little to catch.

Both routes end in the same place: a valid session, replayed from attacker infrastructure, presenting a token your identity provider issued and still trusts.

MFA is an event. Access is a state.

That distinction is the correction worth making at executive level, because it changes what you buy and what you measure.

Multi-factor authentication is an event at a point in time. Access is a state that persists afterward, extended quietly by refresh cycles. In Microsoft Entra ID a refresh token lasts ninety days by default and restarts each time it is used. In our assessment nearly every identity investment of the past decade targeted the event, and very little targeted the state.

The consequences are easy to underrate from a slide deck. Someone inside a live Microsoft 365 session does not need to escalate privilege. They already have the mailbox, the files that user can reach, the chat history, the SharePoint sites, the group memberships. They can read the thread about a pending wire transfer before writing into it. And where an AI assistant has been deployed to answer questions using whatever the signed-in user can already access, it will serve a stolen session as willingly as a real one. The assistant is behaving correctly. Nothing in the request tells it otherwise.

A prediction, labeled as one: machine identity is where this widens next. As agents and automation platforms accumulate long-lived OAuth grants on behalf of employees, organizations create durable access that outlives the password, the laptop, and sometimes the employment. Gaps like that tend to be discovered rather than closed.

Revocation latency is the number nobody measures

Stop asking whether MFA is enabled everywhere. Assume it is. Then assume it will be bypassed, and ask a harder question: from the moment we suspect a session is compromised, how long until that session is dead everywhere?

For many organizations the honest answer runs through a ticket, a business-hours queue, an administrator who knows where the revocation control lives, and an assumption that a password reset terminates sessions already in flight. Microsoft's own revocation table shows how partial that assumption is.

What each action ends in Microsoft Entra ID
ActionPassword sign-insPasswordless sign-insTokens held by server-side apps
User changes or resets their own passwordEndedStay aliveStay alive
Administrator resets the password in the Entra or Microsoft 365 admin centerEndedCookies stay alive; tokens endedEnded
Administrator revokes all of the user's tokensEndedEndedEnded

Two limits apply even to the last row. An access token already issued can keep working until it expires, typically about an hour, unless the application supports continuous access evaluation. And Entra ID cannot directly revoke a session that an application issued for itself.

Four changes shorten the gap. Most are configuration and operational discipline rather than new tooling, though your licensing tier determines what is available to you.

  • Phishing-resistant credentials. Passkeys and FIDO2 keys are bound by design to the legitimate site, so a relay proxy has nothing usable to relay. The credential will not sign for a domain it was never registered to.
  • Device as a condition of access. A Conditional Access policy requiring a managed, compliant device stops a relay that signs in from the attacker's machine, and it is checked again whenever a token is refreshed. In our assessment this is among the most effective controls that tenants are licensed for and have not enforced. It does not by itself neutralize a token copied from a compliant device. Token Protection addresses that for native apps on Windows and Apple platforms; in browsers it remains a narrow preview.
  • Continuous evaluation instead of fixed lifetimes. Exchange Online, SharePoint Online and Teams can act within minutes on specific events: a disabled account, a changed password, newly enabled MFA, revoked tokens, or high user risk. Location rules based on IP addresses are enforced almost at once.
  • A rehearsed revocation path. Someone must be able to terminate every session for an account, at any hour, without escalation. If that capability lives only in one person's memory, it does not exist.

The fourth is operational rather than technical, which is why it is usually the weakest. Revocation is a race, and a phone tree loses it. Whoever staffs your help desk at 2 a.m. needs the authority and the runbook. Run the drill once a quarter and keep the time.

  1. Start the clock. Sign a test account in on a laptop and a phone, then have someone report it as stolen through the normal channel.
  2. Disable and revoke. Disable the account and revoke its sessions. These are two actions. For accounts synchronized from on-premises Active Directory, Microsoft advises disabling there as well and resetting the password twice.
  3. Remove what an intruder would add. Check registered devices, MFA methods, inbox rules, forwarding and application consents.
  4. Close the sessions Entra cannot reach. Sign the user out inside each application that keeps its own session.
  5. Stop the clock when both devices are refused, and record which step took longest.

Three questions before your next security renewal

Token theft does not reward more awareness training. The user in this scenario did nothing detectably wrong; they authenticated successfully to a real Microsoft page. What it rewards is architecture: tying access to devices, replacing shared secrets with origin-bound credentials, watching for valid tokens arriving from implausible places, and being able to end a session in minutes rather than by morning.

Three questions will locate you:

  • Can we require a managed device for access to email and files, and do we?
  • What is our measured elapsed time from suspicion to full session revocation?
  • Who holds long-lived tokens to our data that is not a human being?

An organization that can answer those has stopped treating identity as a checkbox. One that cannot has an MFA deployment and an inflated sense of what it covers, a common position and not an embarrassing one, provided it is temporary. Put the same questions to whoever runs your managed IT and your cybersecurity monitoring.
