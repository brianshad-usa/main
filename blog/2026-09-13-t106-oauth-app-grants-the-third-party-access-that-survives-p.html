The Access That Survives a Password Reset

A password reset can end a token but not the consent behind it. How to inventory, own and revoke third-party and AI app grants in Microsoft 365.

Pro Link SystemsInsights
September 13, 2026 · Updated November 21, 2026
8 min read
In this article
  1. What a password reset retires, and what it leaves on file
  2. The consent screen is a procurement decision nobody treats as procurement
  3. AI assistants widened the permission request
  4. What a defensible grant register looks like
  5. The question worth asking at your next IT review

Reset the password. Revoke the sessions. Collect the laptop. Close the offboarding ticket.

That sequence is correct, and for one entire category of access it is beside the point. The person's credentials are gone. The software an administrator once approved on the company's behalf still has its own identity in the tenant, still holds its permissions, and is still reading mail or files on a schedule nobody remembers approving.

These are OAuth application grants. They are the connective tissue of a modern Microsoft 365 environment, the mechanism by which a scheduling tool reads calendars, a CRM syncs contacts, a backup product touches SharePoint, and an AI assistant learns enough about a business to be worth its subscription. They are also, in our assessment, the least governed form of standing access in the average mid-sized company. For the executive who answers for access and the IT lead who inherits it, the decision is whether each grant gets an owner and an end date.

What a password reset retires, and what it leaves on file

Access to a cloud tenant is token-based at the moment of use. A user authenticates once, a token is issued, and software presents that token rather than re-authenticating a human every time it needs something. That is a property of the protocol, not a configuration choice.

Precision matters here, because the common assumption is wrong in an instructive way. When a user changes their own password, tokens held by a server-side application stay alive. When an administrator resets it from the Entra or Microsoft 365 admin center, those tokens are revoked. In neither case does the agreement change. The consent record stays exactly where it was, and the next time the user signs in to that application it receives a fresh token with no new prompt. Permission was interrupted, never withdrawn. The FBI said the same of malicious apps in September 2026: changing the password does not revoke the token, and the app itself has to be removed.

Grants come in two shapes, and the difference governs how an executive should reason about the risk.

  • Delegated permissions. The application acts on behalf of a specific user and can reach only what that user can reach. Disabling the account cuts off the application's access to it, so this kind is constrained by the person's lifecycle, provided the account is actually disabled.
  • Application permissions. The application acts as itself, through its own identity in the directory, with its own credentials. No user sits behind it. No password. No multi-factor prompt. No human whose departure would ever trigger a review.
What each response step ends, and what it leaves
StepEndsLeaves in place

Revoke all sessionsEvery refresh token for that userThe consent record, app-only access
Disable the accountDelegated access for that userThe consent record, app-only access
Revoke the delegated grantThat application's delegated accessThe user's ability to consent again, unless policy blocks it
Remove the application permission, or disable the applicationWhat the application could do as itselfAccess tokens already issued, until they expire

Revoking sessions is one administrative action. Removing an application's consent is a different one, in a different part of the admin center, and it is the only step that reliably ends the relationship. For consent given by individual users, Microsoft's portal shows the grant but removing it takes Graph or PowerShell. Find out whether your offboarding checklist, usually run from the help desk, performs both actions or only the first.

Application permissions are the sharper edge. Because such an app holds its own identity, the Conditional Access policies written for people do not apply to it. Microsoft offers a separate Conditional Access for workload identities, but it covers only single-tenant applications registered in your own directory; third-party and multi-tenant software is out of scope. For a vendor's application, the permission itself is the control. Offered as analysis rather than alarm: an attacker who obtains a vendor's application credential inherits access that never appears in the user sign-in log most teams watch. It is recorded separately, as a service principal sign-in, and it looks like the integration the finance team asked for in March.

The consent screen is a procurement decision nobody treats as procurement

A department head evaluates a promising tool. The trial opens with a dialog box requesting permission to read mail, read all files the user can access, maintain access to data it has been given access to, and sign in on the user's behalf. Accept. The pilot proceeds. The vendor is never selected, the project dies quietly, and the grant remains.

Whether that click still works depends on a setting. Microsoft's managed consent policy, the default for new tenants, now requires an administrator for mail, calendar, file and Teams chat permissions, apart from a short list of popular mail clients. Tenants with older or custom settings may still allow it, and tightening the setting does nothing to grants already made.

Weigh the asymmetry honestly. Most organizations have a purchasing process for a software contract of any meaningful size: quotes, security questionnaires, perhaps legal review. The same organization may let a manager, or a hurried administrator, hand an unvetted vendor persistent programmatic read access to executive mailboxes at no cost, in a single click, with a record that nobody outside IT would ever see. Nothing malicious is happening. The imbalance is architectural, which is why it is worth fixing at the policy layer rather than by asking people to be more careful.

App consent is best treated as a cybersecurity control and a third-party risk control at the same time. A grant is a contract. It simply is not filed anywhere a CFO would think to look.

AI assistants widened the permission request

The genuinely new pressure in 2026, again as analysis rather than prophecy, is that an assistant's usefulness scales with the breadth of what it can read. A tool that sees one folder is a novelty. A tool that sees the mailbox, the drive, the meeting history and the chat archive becomes the thing people refuse to work without. Vendors understand this, so requested scopes have widened, and requests for offline access, the ability to keep working while nobody is signed in, read as standard rather than exceptional.

Agentic tools push further still. An agent that files expenses, drafts replies or updates records needs write permission and needs to act unattended. That profile deserves a named owner, a review date and a documented business justification. Too often it arrives through the same dialog box as a calendar plug-in.

Shadow AI is usually framed as a data-leakage problem: staff pasting confidential material into consumer chatbots. That framing is incomplete. The more durable exposure is the grant left behind: an application nobody uses anymore that still holds standing permission to read everything, with a client secret sitting on a server operated by a company whose security posture was never assessed and whose acquisition you will not hear about.

What a defensible grant register looks like

None of this requires an expensive platform. It requires treating grants as inventory. For Los Angeles companies in the twenty-to-five-hundred-seat range, the work is narrow and finite:

  • Restrict user consent and route requests through an admin consent workflow. People can still ask. Someone accountable answers.
  • Enumerate every enterprise application in the tenant and separate those holding application permissions from those acting for a user. The first list is usually shorter and deserves real scrutiny.
  • Assign a human owner and a review date to each retained grant. An application with no owner is an application to remove.
  • Track credential expiry for app secrets and certificates you manage, so integrations fail during business hours rather than at two in the morning.
  • Revoke deliberately, not in bulk. Some of these grants are load-bearing. Disable sign-in for the application first, because that can be undone, then follow a disconnect sequence once you know what broke.
  • Add grant revocation to two runbooks: employee offboarding and vendor offboarding. Ending a contract should end the access.
  • Include app-only access in identity-compromise response. If an account is breached, revoking sessions is insufficient when the attacker registered a grant first.

The initial pass is a finite project. Maintained afterward, it is a quarterly conversation.

The question worth asking at your next IT review

Ask your IT leader or managed IT provider for a list of every third-party application holding standing permission in the tenant, sorted by the breadth of what it can read, with an owner named beside each entry. The list itself is the deliverable. If it cannot be produced quickly, that gap is the finding, and it is more useful than another debate about password policy.

The executive point is narrow and should outlive this article. Identity is the perimeter, and that perimeter now includes software that never sleeps, never leaves the company and never forgets what it was once allowed to do. Governing people is table stakes. Governing the grants those people issue is the part that still needs an owner.
